# AGENTS.md

Throwaway test harness for a large-document (500-1000 page) legal AI pipeline. Read these first:
- `docs/legal-app-pipeline-context.md` (architecture, task rules, decisions)
- `docs/pipeline-harness-context.md` (harness plan)

## Stack
- React + Vite SPA (`src/`), TypeScript
- `docx` produces the Word export in the browser; no server build step.
- Library DOCX/text/image conversion runs in a lazy module worker: `mammoth` (DOCX → HTML), `jspdf` (PDF writer, MIT), committed Noto Sans / Noto Sans Devanagari fonts (SIL OFL 1.1). The main bundle does not include either library.
- Browser IndexedDB via `idb` (documents with PDF Blob, pages, chunks, embeddings, tasks, raw_responses, ocr_decisions, run_state)
- Supabase (local CLI + Docker): Postgres, Auth, Edge Functions. RLS off (throwaway) for `runs`, `task_results`, `reports`, `rate_limits`; RLS on with owner-only policies for `chat_sessions` and `chat_messages` (migration 0004). Pending (P8): enable owner-only RLS on the older tables too.
- Hosted Supabase for the app shell: `npm run dev:hosted` reads `.env.hosted`; local `npm run dev` reads `.env.local`. The `ai-proxy` proxy is the same function in both. See `docs/hosted-supabase.md`.
- OpenRouter via the `ai-proxy` Edge Function. The key lives in `supabase/functions/.env`, never in the browser. The function sends CORS headers for hosted browser preflights; `ALLOWED_ORIGIN` (optional, comma-separated) locks the allowed origin.
- Default model: `deepseek/deepseek-v4.1-flash`.

## Folders (under `src/`)
- `ingest/` pdf.js extraction, page quality, Tesseract OCR, OCR output check, clause chunker, fingerprints, storage check. `ingest.worker.ts` runs the pipeline off the main thread.
- `runner/` IndexedDB layer, `runTask`, worker, client (plain TS, no UI imports)
- `tasks/` task types, fingerprint, parse, split, validation
- `retrieval/` embeddings in a worker (transformers.js), Unicode tokenizer + MiniSearch keyword index, RRF hybrid search, law stand-in, definitions sheet
- `quality/` pure scorers over saved runs, golden thresholds, repeat-run comparison, regression config and score history (no UI imports)
- `drafter/` draft storage (separate `legal-drafter` IndexedDB), local-first Supabase sync, title derivation, reference resolution (plain TS, no UI imports)
- `ui/` React pages only
- `ui/app/` the app shell: router, sidebar, login gate, theme, placeholders (UI only)
- `ui/library/` document library page, preparation orchestrator, status derivation, ingest-worker wrapper, local removal, multi-file import queue (`importQueue*.ts`), conversion metadata, and `convert/` (DOCX/text/image → PDF, worker, fonts, fixtures)
- `ui/drafter/` drafts list and Brief form (UI only)
- `lib/` shared Supabase client for the app shell (one persisted session per project)

## App shell (routes)
- `/` redirects to `/chat`; the app shell owns the router. The harness pages stay at `/?page=...`.
- `/chat` and `/chat/:sessionId` are general chat (see "Chat" below). `/compare` is a placeholder route kept reachable by URL but not linked from the sidebar or anywhere else.
- `/help` is the plain-language Help page (see "Help page and guidance" below). Its sidebar entry sits below the module entries, above the sidebar footer.
- `/draft` lists drafts; `/draft/new` and `/draft/:draftId` are the Brief form, `/draft/:draftId/plan` is the plan, `/draft/:draftId/outline` is the structure, `/draft/:draftId/sources` checks the bound sources, `/draft/:draftId/write` writes the document, `/draft/:draftId/review` reviews and downloads it (see "Drafter" below).
- `/documents` lists IndexedDB documents, imports PDF/Word/text/image files (multiple files, or drag-and-drop) and runs the whole preparation (ingestion, embeddings, index, definitions) one file at a time, removes a document from this device.
- `/documents/:docId/review` is the in-app review screen (page image beside OCR text, three equal decisions: Accept text, Save corrected text, Leave blank, plus Proceed without reviewing). Accept with empty text saves a blank page. Needs-review rows and the Review action open it; the harness page is not linked from the library. After the last page is resolved it starts preparation and returns to `/documents`.
- `/analysis` lists ready documents; `/analysis/:docId` is the Deep Analysis page (Ready documents only, see "Deep Analysis page").
- Status: `ready` → Ready (with "Ready · N pages not reviewed" when pages were waived); `review` → Needs review (N pages); `new`/`processing` → Preparing. The library's Ready is the durable preparation result (see Document preparation); the document-level `status` stays the ingestion status.
- Login: Supabase Auth email+password. The app shell and the harness pages share one persisted session (same project URL, same localStorage key).
- "Remove from this device" deletes the document, pages, chunks, OCR decisions, embeddings, definitions, analysis reports/state, tasks and run state for that document. It refuses while a preparation or analysis lock is held. Supabase reports are kept.
- Theme: light/dark, scoped to the app shell; the harness pages keep their look.

## Help page and guidance
- `/help` is one readable column: the "Before you start" intro, then Documents, Deep Analysis, Chat and Drafter sections with anchors `#documents`, `#deep-analysis`, `#chat`, `#drafter`. Content comes from one file, `src/ui/help/helpContent.ts` (typed sections: id, title, whenToUse, steps, tip). Anchors scroll into view on arrival.
- The four module list pages (Documents, Deep Analysis, Chat, Drafter) show one muted "When to use this" line linking to the matching Help anchor. Where an existing description says the same thing, the shorter of the two is shown and the duplicate is hidden. Sub-screens have no line.
- Every module page has a "How to use this page" button in the page header's title row, right-aligned on the same line as the title (accent style, not muted); on narrow screens it wraps below the title and stays right-aligned. Other page actions (OCR language, Import documents, New draft, Back to drafts, status chips) stay in their own right-aligned row below the title and description. The button opens an accessible pop-up (`src/ui/Modal.tsx`: focus trap, Esc, click outside, focus restored, body scroll locked) with the page title, 3–5 numbered steps and "Read the full help" to `/help#<module>`. Steps come from one file, `src/ui/help/pageHelp.ts`; page ids are `documents`, `analysis-list`, `analysis-report`, `chat`, `drafter-brief`, `drafter-plan`, `drafter-outline`, `drafter-sources`, `drafter-write`, `drafter-review`. The drafts list reuses `drafter-brief`. Only the main header of a page gets the button, not loading/not-found headers.
- The Deep Analysis page shows a prominent notice under the start inputs, directly above Start: it stays visible always. Pressing Start first opens a "Before you start" pop-up (`src/ui/analysis/StartNotice.tsx`) with the same text and two large buttons; "Do not show this again" (`localStorage` `legal-app.hideStartNotice`) makes Start run directly, while the notice below the inputs stays. The pop-up only gates the call to the page's existing start handler; Resume and Retry are not gated.
- `src/ui/KeepTabOpen.tsx` renders "Keep this tab open until this finishes. You may use other tabs or programs." only while a job is active: Documents (a document is preparing or a queue file is converting/preparing), Deep Analysis (`running`), and Drafter Write (`running`). Those three use the prominent style; it adds no state.
- Behaviour behind the reminder: document preparation and the Drafter writer are module-level and keep running when the user moves to another app page; Deep Analysis does not and needs its page kept open (leaving disposes the retrieval worker the run still uses). Closing or reloading the tab stops any of them; saved progress can be resumed.
- Leave warning (`src/ui/useLeaveGuard.tsx`, pure wording/decisions in `src/ui/leaveGuard.ts`): while a job is active it captures in-app links, guarded `navigate` calls (Documents row/queue actions) and browser Back, and shows a "Please stay on this page" modal with "Stay on this page" (default) and "Leave anyway"; Esc or clicking outside means Stay. Browser close/reload shows the browser's own prompt (`beforeunload`). It does not cancel anything. Documents preparation/import queue and Drafter writing say the job keeps going on another app page but stops on tab close; Deep Analysis says a page change stops or may fail the run. Chat is not guarded. A same-URL history sentinel makes Back land on the page so it is not torn down before the modal; it is removed when the guard goes inactive. Tests: `src/ui/leaveGuard.test.ts`.
- The sidebar list is `src/ui/app/navItems.ts`: Documents, Deep Analysis, Drafter, Comparator, then Help. Comparator is a separate app opened in a new tab: the entry is a sidebar button (not a route link, never shown as active) that opens a "Comparator (beta)" notice (`src/ui/app/ComparatorEntry.tsx`) with Cancel and a real `Open Comparator` anchor (`target="_blank"`, `rel="noopener noreferrer"`); Esc, click outside and Cancel close it with no navigation, and focus returns to the entry on close. Its address comes from `VITE_COMPARATOR_URL` and only an absolute `https` value is used; when it is unset or invalid the entry is hidden. No app tokens, session data or query parameters are added to the URL, and the leave guard never fires (the entry is a button and the anchor targets a new tab). `/compare` and its page are unchanged.

## Document preparation (library)
- "Import documents" runs the whole preparation in one go: ingestion (extract, OCR, page decisions, chunking), then embeddings, then the keyword-index warm-up, then the definitions sheet. The library is the only orchestrator; the pipeline modules are unchanged.
- The orchestrator lives in `src/ui/library/prepare.ts` outside React. It survives route changes (one preparation per tab), and the per-document `navigator.locks` lock (`doc:<hash>`) still blocks another tab. Progress is written to `localStorage` (`legal-app.prep.<docId>`) and pushed to the library, so navigating away and back keeps the progress live.
- Stages are skipped when their durable result exists: chunks on the document, `embedding_state` with `completedAt` and the matching preparation fingerprint and embedding model version, and a `definitions` record with the matching preparation fingerprint. A document already prepared in the harness (no wrapper state) reaches Ready without re-running those stages.
- The keyword index is derived in the retrieval worker, not persisted. Preparation warms it with a search call; the Search page rebuilds its own index. A document with no definition/party text gets an empty `definitions` record so it can reach Ready.
- `Ready` is the durable preparation result: `doc.status === 'ready'` plus chunks, embeddings and a matching definitions sheet. The document's `status` stays the ingestion status; a ready document with a missing stage is `Preparing`.
- Status: Preparing (stage + progress bar) / Needs review (N pages) / Ready / Failed (stage + reason + Retry). A review document pauses and waits for the user; the review page continues the preparation automatically after the last page decision. A failed stage is retried explicitly; partial definitions (some failed tasks) are treated as failed.
- Proceed without reviewing (library row and review screen, after a confirm): every page still needing review (`status` review, or already waived) gets an `ocr_decisions` row with `decision: 'waived'` holding its extracted text. The page is `accepted` with `source: 'waived'` (so it is never shown as human-confirmed), and an empty page stays empty. Ingestion then finalizes and preparation continues to Ready with no special casing. Pages a person already decided are not touched. The waiver is one IndexedDB transaction (`src/ingest/review.ts`).
- Waived pages stay reviewable. A manual decision replaces the waiver (source `manual`). A recheck on the harness page keeps every decision, waived included.
- Ready with waived pages shows "Ready · N pages not reviewed" (tooltip on the chip) and a Review action. Failed definitions on such a document follow the normal path (Failed, Retry); no special bypass.
- Resume: a review document with zero unresolved pages (tab closed after Proceed, before finalize) resumes automatically on the next load. A document with unresolved pages still waits for the user.
- `runPreparation` honours `forceIngest` and `recheck` even for a prepared document; the review screen uses `forceIngest` to re-ingest after each decision. Preparation is not started while another document is being prepared in the tab.
- The review screen offers three equal secondary buttons: Accept text, Save corrected text and Leave blank. Accept on empty/whitespace text takes the Leave blank path (same blank record, no warning). After a decision is saved and no page is still unresolved (`status` review, or already waived), it starts preparation and returns to `/documents`; if preparation cannot start it stays and shows the existing error. Previous/Next and Proceed without reviewing are unchanged, and Proceed does not auto-return.
- The review screen disables decisions while a preparation runs for the same document (a decision during a run could be skipped by the run's finalize).
- Decisions are shared by the harness page and the review screen (`saveReviewDecision`). The harness page keeps its Retry OCR; the review screen no longer offers Retry OCR, Recheck or Leave unresolved. A saved decision still wins on a later recheck (existing behaviour, not changed).
- Analysis reports carry `unreviewedPages` (count of waived pages when the run was saved). The report shows a separate "Pages not reviewed." banner, also in exports. Older reports have no count and show no banner.
- "Retry" re-runs the failed stage; "Remove" deletes the document and its local state. `preparedAt` and the prepared fingerprint (including the embedding model version) are stored on Ready.

### Import queue and file conversion
- "Import documents" and drag-and-drop accept many files: PDF, Word `.docx`, text `.txt`/`.md`, image `.png`/`.jpg`. Common unsupported types (`.doc`, `.rtf`, `.xls/.xlsx`, `.ppt/.pptx`) are in the picker so the user gets a plain message; each is skipped, the rest continue.
- Files are queued and prepared one at a time through the existing `runPreparation` path. `prepare.ts` and `preparationState.ts` are not changed by this work. The queue waits for the tab's active preparation to finish, so "one preparation per tab" and the `doc:<hash>` lock still hold. A needs-review file pauses only itself and the queue continues; a failed file does not stop the queue either.
- `src/ui/library/importQueue.ts` is the pure queue engine (injected dependencies, tested). `importQueueInstance.ts` is the singleton wiring and lives outside React, so changing route does not stop the queue. Closing or reloading the tab loses files still waiting; a file already preparing is a document and resumes from the library. The panel says this.
- Conversion runs before the import path in a lazy module worker (`src/ui/library/convert/`): mammoth for DOCX, jsPDF for the PDF writer, committed Noto Sans / Noto Sans Devanagari fonts. PDFs pass through untouched. TXT/MD become text PDFs with headings/paragraphs/lists/simple tables. Images become one page each so the existing OCR pipeline handles them. No new ingestion code path.
- Converted text pages have a real text layer that pdf.js extracts, so `assessNativeText` calls them native and no OCR runs. Devanagari is preserved in logical order (correct extraction) but is not shaped for print; a visible warning says so. A glyph missing from the built-in fonts is replaced with a visible substitute and warned about, never dropped silently. Pictures in a DOCX are not included (warning).
- Determinism: fixed PDF creation date, file id from the input hash, no timestamps or random ids. Re-importing the same DOCX/TXT/MD/image produces identical converted bytes and hits the existing content-hash duplicate check. A later converter or font change changes the bytes, so an old converted document will not dedupe against a fresh conversion.
- The document keeps the original file name (`Lease.docx`); size and page numbers refer to the converted PDF. The converted note is in localStorage `legal-app.converted.<docId>` (`src/ui/library/conversionMeta.ts`): "Converted from Word · Page numbers refer to the converted version", warnings, original name/size. No `pipeline-harness` schema change. Removal clears it.
- `VITE_LIBRARY_MAX_FILE_MB` (default 50) limits converted types only; PDFs keep today's no-added-limit behaviour. Conversion is off the main thread. The built worker chunk is ~743 kB minified / ~234 kB gzip; the two fonts are ~569 kB and ~219 kB raw (~286 kB / ~95 kB gzip), fetched only for text conversions.
- Tests: `importQueue.test.ts` covers sequential processing, failure isolation, needs-review not blocking, duplicate reuse, unsupported and oversize files, retry and removal. `prepare.guard.test.ts` locks the guarantee that a needs-review pause releases `getActiveDocId()`. `convert/convert.test.ts` covers DOCX/TXT/MD/image text extraction, deterministic bytes, corrupt/unsupported failures and the native-text/OCR verdicts.

## Tables
Supabase: `runs` (with `source`, `chat` for chat-originated runs), `task_results`, `reports`, `rate_limits`, `chat_sessions`, `chat_messages`, `drafts` (RLS owner-only, migration 0006). RPCs: `save_task_result(p_row jsonb)`, `increment_rate_limit(p_user, p_window)`.
IndexedDB (`pipeline-harness`): `documents`, `pages`, `chunks`, `embeddings`, `embedding_windows`, `embedding_state`, `definitions`, `analysis_reports`, `analysis_state`, `tasks`, `raw_responses`, `ocr_decisions`, `run_state`.
IndexedDB (`legal-drafter`, separate database, v1): `drafts`, `draft_deletions`.
Library documents are **device-wide, not per-user**: `pipeline-harness` has no user column, so every signed-in account on this device sees the same documents. Drafts and chat are per user (`userId` locally, RLS remotely). This is a known gap, not a design decision.

## Key rules
- `runTask` is plain TypeScript. No DOM, no Edge APIs.
- Save the raw response to IndexedDB before parsing it.
- Each JSON item is validated separately. Valid items are kept.
- `finish_reason=length` never accepts the output. The piece is split into `${id}/a` and `${id}/b`.
- A stream with no `finish_reason` is `stream_interrupted`, never parsed.
- A task is `done` only after `save_task_result` succeeds.
- Idempotency: `task_results` is unique on `(task_id, fingerprint)`. The fingerprint excludes the model.
- Each attempt has an `attempt_id`. Results from superseded attempts are dropped.
- Retry only: `timeout`, `network`, `stream_interrupted`, `bad_json`, `validation`, `http_429`, `http_5xx`. Max 3 retries, then the fallback model on the last attempt.
- The proxy returns the provider's error message with `http_4xx`/`http_5xx`; `runTask` stores it as `failureMessage` on the task and `failure_message` on `task_results`, and the failed-task table shows it.
- `http_401`, `http_400`, `http_403` and `length` at the minimum size fail immediately.
- A task found in `requesting` on startup becomes `uncertain` and gets one new call.
- A task in `received` with a saved raw response is parsed and saved again with no new AI call.
- Supabase `runs.status` is authoritative. If Supabase is unreachable, the runner pauses, not fails.
- One runner per document, enforced by `navigator.locks` (`doc:<docHash>`, `ifAvailable`).
- Concurrency is `VITE_CONCURRENCY` (default 3) inside `executeTasks`, with one claim per task per round and one shared backoff gate so concurrent workers pause together after `http_429` / network / `http_5xx`.
- Show "AI-assisted, requires lawyer review" on all outputs (later prompts).

## Pages (dev)
- `/` the app shell (sign-in, Documents, Chat, Deep Analysis, Drafter, Comparator)
- `/chat`, `/documents`, `/analysis`, `/analysis/:docId`, `/draft`, `/compare`, `/help` the app routes
- `/?page=test` the Prompt 1 task test page
- `/?page=ingest` the ingestion page (upload PDF, OCR language, Start/resume, Recheck, review, chunks). `&doc=<id>` opens a document directly.
- `/?page=search` embedding progress, hybrid document search, law stand-in search, definitions sheet
- `/?page=analysis` clause analysis, verification, roll-up, cross-clause pass, ledger, metrics, Ask (retrieval / whole-document), custom prompt, restore, forced-failure and fallback checks
- `/?page=quality` quality suite: per-document scores, thresholds, hold-outs, misses/drops, repeat-run comparison, regression set and stored score changes
- Ingestion: a page is Ready only when every page is native/ocr/accepted/blank and chunks are saved. Decisions in `ocr_decisions` win over reprocessing (accept, correct, blank, unresolved, waived). The only ingestion change for review work is the `waived` branch in `processPage`; OCR, extraction, chunking and fingerprints are unchanged.
- OCR is multi-pass and document-neutral: 200/300/400 DPI, PSM 3/4/6, and grayscale/Otsu preprocessing; the best attempt is chosen by `checkOcrOutput`, confidence and word count. Page records store confidence, words and PSM for review.
- pdf.js assets: `scripts/copy-pdfjs-assets.mjs` copies `wasm/`, `cmaps/` and `standard_fonts/` from `node_modules/pdfjs-dist` into `public/` on predev/prebuild/pretest. `openPdf` passes `/wasm/`, `/cmaps/` and `/standard_fonts/`; without them CCITT/JBIG2 masks decode to an almost blank page.
- If a rendered page has more than one image object but under 1% ink, the page is marked `render_decode_failed` instead of being OCR'd as a blank page. The review panel and log show a wasm-asset hint.
- Regression tests: `tests/pdfjs-assets.test.ts` checks the wasm/cmap/font routes (wasm as `application/wasm`); `tests/golden/arihant.test.ts` renders a CCITT-mask page and checks real ink (conditional on the attached PDF).
- Chunking: top-level clauses must continue the numeric sequence (`N)` primarily, `N.` legacy). `(a)`, `(i)`, `a)`, `(N)` stay inside the clause. Lettered recitals continue A..Z with one restart allowed. Table rows are never boundaries (Sr./no. headers, numbered name/amount rows, bare `N text`).
- Chunking restarts: a low top-level number after a real run, or a `Schedule`/`Annexure`/`Part`/`Article`/`Chapter` heading or a page-title block, starts a new numbering run and records a section break. A table row never restarts numbering.
- Hard clause limits: `maxClausePages` (15) and `maxClauseTokens` (6000). An over-limit clause is force-closed at the next heading-like line and marked `unusuallyLong`.
- A size-split part keeps its own `pageStart`/`pageEnd` and its own `pageMarkedText`; analysis input uses that stored text and never re-slices pages by a clause range.
- Chunk confidence: after chunking, the page gaps/overlaps, missing/repeated clauses, size/input limits, long clauses, shared page ranges and clause-count plausibility decide whether to keep structured chunks or rebuild structure-free (~1000 tokens, sentence cuts, short overlap). The chosen mode and reason are stored on the document and shown in the Chunk check panel. Chunks that fail size or page-range checks are never sent.
- `checkChunks` (shown as the "Chunk check" panel) reports page gaps/overlaps, above-max chunks, chunks above the model input limit, bad starts, missing/repeated clauses, size-only clause splits, section breaks, clauses over N pages and shared page ranges. A separate analysis-chunk check shows the same for the smaller analysis chunks.
- The pre-flight guard in `runTask` estimates prompt+input tokens and fails locally as `input_too_large` before any model call; the provider's error message is stored as `failureMessage`/`failure_message` and shown in the failed-task table.
- Partial analysis runs are marked `partial`; the report lists failed clauses (number, pages, code, message), adds "N of M clauses not analysed" to the overview, labels missing claims as unverified, and is `unreliable` when more than 10% of clause units fail. "Retry failed only" splits oversized inputs and retries up to five failed units.
- Structure-free coverage is chunk/page based: "N of M chunks analysed, pages covered X of Y", with failed chunks listed by page range. Model-reported clause numbers are not used as a manifest in this mode, and the UI hides clause labels.
- Verified items repeated across overlapping chunks (same page and equal/heavy quote overlap) are deduplicated; the report records items and clauses before/after.
- Failed clause chunks are retried once after the pass with a backoff delay. Over-length section summaries are split into two smaller groups instead of failing.
- Analysis metrics include 429 events and total 429 wait time. `autoReduceConcurrency` lowers concurrency after repeated 429s (default on).
- Supabase sessions refresh before proxy calls and once on a 401; the local edge runtime uses `verifyJWT:true` with ES256 JWKS, so a stale/invalid user JWT appears as `UNAUTHORIZED_ASYMMETRIC_JWT` or `auth_required`.
- Golden test: `tests/golden/hiramoti.test.ts` reads `HIRAMOTI_PDF` (or a known local path) and skips if the PDF is absent.
- Golden scoring: every `tests/golden/<doc>.json` is read by the quality page in the `{doc, holdout, note, expected:[{clause, token, kind, contains?, reason?}], removed:[...]}` format. `kind` is `payment`, `date`, `obligation`, `favour` or `risk`. A file with `"holdout": true` is scored but excluded from the tuning aggregate. A bare clause matches its sub-items; a sub-item expectation needs the same sub-item.
- Quality scorer: pure functions in `src/quality/` read saved `analysis_reports` and stored pages, never call a model, and report recall (model and model+code for payments), precision on listed items, quote validity against the cited page, false "missing" claims, ledger-versus-task counts and overview figure fidelity. Favour recall uses the judgement snapshot attached to a saved report. Scores are kept in localStorage and compared with the previous stored run.
- Repeat-run comparison runs the analysis twice on one document and reports matching verified items plus items seen in only one run.
- The planted-fact tool (`scripts/plant_facts.py`) writes a synthetic text PDF and a matching golden file; `tests/golden/planted.test.ts` checks the facts are on the recorded pages and scores it without a model call.
- Embeddings: `Xenova/multilingual-e5-small` q8, version `...@q8-v1`, `passage:` for chunks, `query:` for questions, windows ≤400 tokens pointing at a parent chunk. Vectors store model + modelVersion + prepFingerprint; a mismatch re-embeds.
- Definitions use a non-reasoning model: set `VITE_SEARCH_MODEL` (e.g. `openai/gpt-4o-mini`). Reasoning models can spend the whole output budget on reasoning and return no JSON; that now fails as `empty_output` instead of splitting.
- Analysis runs on separate small chunks (~700 target / 1200 max tokens) with `[[pN]]` page markers. Quotes are located on the cited page, then the chunk range, then the whole document; page/clause are taken from where they are found, and page corrections are counted.
- Clauses with no model entry are listed as skipped and retried once with a clause-only input. Judgement (whole-document Ask) uses the same resolver and one focused retry for chunks with no finding.
- Judgement directions are `favours_a` / `favours_b` / `neutral`, where A and B are the two agreement parties in definitions-sheet order. Party names come from the sheet, never from fixed text. Any clause with lettered or roman sub-items is packed into small sub-item groups and checked on its own. A burden on a party is never reported as a benefit to that party; obvious cases are reclassified as neutral.
- Document type: one classification call stores `agreement` / `lease` / `deed` / `notice` / `other` on the document (`docType`). It only chooses an extra prompt checklist; unknown or `other` uses the general checklist.
- Chunker numbering: `N.`, `N.N`, `N.N.N`, `N)`, `(N)`, `Clause N`, `Section N`, `Article IV` and `ARTICLE N: TITLE` are detected by the sequence rule (the next number continues the previous). `(N)` and `Section N` also appear as lists, so in a document that uses dotted or paren clauses they must continue a run of the same style. Table rows and numbered lists inside a clause are never boundaries.
- Anchors: sub-item labels follow their own sequence (a..z, then aa, bb, ...), and a unit with no clause number of its own keeps the preceding clause as its prefix.
- Analysis uses `VITE_ANALYSIS_MODEL` (fallback `VITE_SEARCH_MODEL`, then `VITE_MODEL`), reasoning minimal. Prices per 1M tokens: `VITE_PRICE_INPUT_PER_M` / `VITE_PRICE_OUTPUT_PER_M`. Budget starts at 2600 and is replaced by ~1.5× the measured p95 completion tokens after a run.
- Every quoted item is verified against the cited stored page (whitespace/quote/dash/hyphen normalised). Unverified items are dropped and counted, never shown. Roll-up sentences must cite a valid item ID or they are dropped.
- The report is saved to `reports` (Supabase) and `analysis_reports` (IndexedDB); with local state cleared, the page restores it from Supabase.
- `VITE_FALLBACK_MODEL` is used by the fallback check (three forced transient failures, then the fallback on attempt 4).

## Deep Analysis page (`/analysis/:docId`)
- Start screen: Matter, Detail level (brief/standard/detailed: clause summary length and overview sentences), Focus (steers the risk checks only), Custom prompt (optional). The pre-run estimate is an upper bound (`costEstimate.ts`) and includes the custom pass when the prompt is filled: the coverage reads, one answer call per request part, and up to one cut-off retry per part.
- Start, Resume (interrupted run) and "Retry failed only". The page keeps a per-document run record in localStorage (`legal-app.analysis.<docId>`) until a run finishes with no failed tasks.
- After a run finishes in this visit and a report is shown, the page scrolls the export bar and report into view once, after one animation frame. The scroll target wraps both, so the Export buttons are fully visible above the report title. It scrolls only when that block's top is below 100 px (an already visible or already entered report does not move), uses smooth scrolling unless the user prefers reduced motion, and does not fire on load, a restored report or a failed run with nothing shown. Retry failed only scrolls the same way. Pure decisions are in `src/ui/analysis/reportScroll.ts`.
- Retry: `runAnalysis({ resumeRunId, retryFailed: true })` resets failed tasks of the planned passes to `queued` and re-runs them with their original input. Finished results are reused and never called again. The report is then rebuilt from stored results. A failed chunk that finished on a later pass is no longer counted as failed.
- A run and removal both hold `doc:<hash>`; removing a document is refused while a run or preparation holds it.
- Clause call (`clause-analysis-v3`) returns risk priority/basis/suggestion/laws, `missing` and `prose`. Risk priority is High only for void/unenforceable, illegal, statutory-violation or major-financial bases (`rubric.ts`). Law references are names only, labelled "model knowledge, applicability unverified".
- Custom prompt pass (`promptPass.ts`) runs per analysis chunk; answers are verified against the cited page; duplicates merged.
- Report model (`reportModel.ts`, pure, shared with the exports): sections numbered in code (Prompt Result only when used); Defined Terms absent. Unnumbered entries are placed by their verified quotes, then by their chunk's clause list (`chunkClauses`), else kept as separate rows and counted. Numbered entries with the same clause number merge: longest non-empty text per field, unioned lists, deduplicated items. Merge stats appear in the Clause Breakdown.
- Prose fields (summary, conditions, rights, etc.) are model-written and cited to clause/page. Quoted text is always verified text. Dates, Amounts and Location mismatch rows appear only when present.
- Citation click opens the stored PDF page in a right-hand panel; the quote is highlighted by `citationLocate.ts` when it can be found on the page.
- Export (`src/export/`): `blocks.ts` turns a `ReportModel` into one ordered block list (title, metadata, static TOC, headings, paragraphs, lists, tables, footer). The DOCX (`docx.ts`) and HTML (`html.ts`) writers render only those blocks, so both match the screen exactly and neither invents content. Exports are built from the in-memory model, so a report restored from Supabase exports identically.
- DOCX: real tables, built-in Heading 1/2/3, static TOC (numbers and titles, no page numbers), footer with "AI-assisted, requires lawyer review" and page numbers, citations as "Clause N · p. X", model-written labels kept, priority as plain text (no shading). Headings keep with the following table.
- HTML: one self-contained file (inline CSS, no external requests), light and dark by preference, print rules, repeated table headers. The TOC is a list without markers because the numbers are in the text.
- Export bar on the report view; file name is the document name plus the date. Large reports show clause progress and yield every 20 clauses while blocks are built.
- `scripts/render-export-check.ts` renders the fixture for a LibreOffice/PDF layout check (bundle with esbuild; not part of the app).
- Reviewing for (Licensor / Licensee / Neutral, default Neutral) is stored with the run. It frames risk priorities, suggestions and the custom answer only; it never limits what is reported.
- Risk prompt lists material one-sided patterns (repairs on one party, penalty formulas, entry without notice, asymmetric notice, forfeiture, unilateral escalation, court waivers), adds statutory costs shifted wholly to one party, and marks asymmetric notice/termination as at least Medium. High-eligible examples: waiver of access to courts, total forfeiture of a large deposit, compounding unilateral escalation. High guard unchanged.
- Missing pass: gets the clause list and the document type; the prompt asks for up to 10 absent typical protections. A hit covers a claim only when its matched text contains the topic's own words: the full phrase, or every non-generic core term compared by six-character stem (`refund` matches `refund mechanics`, `indemnity` matches `indemnify`). Generic words (`law`, `act`, `clause`, `party`, `agreement`, `document`) never cover on their own. Coverage also needs a keyword hit with fused score at least 1/110 (`COVER_MIN_FUSED`). A weak vector-only hit keeps the claim as verified missing. A failed or empty search keeps the claim in a separate "Possibly missing (not verified by search)" list, never used by the summary gap guard. Stats "N proposed, M kept, K dropped by search; pass ran: yes/no; raw items: N; rejected by schema: M" and a dev-visible dropped list (topic and hit page) are stored and shown in the Risk Register. Item shape is tolerant (`topic`/`title`/`protection`, `text`/`description`/`detail`); unusable items are counted as rejected, never reported as zero proposed. A group cut off at the output cap (`failureCode=length`) is retried as two smaller calls, not with a larger cap.
- Overview: 13 points (no Risk Allocation point) as short cited paragraphs, 3-5 sentences scaled by detail level. Points 10 (Statutory Compliance), 11 (Notable Drafting Issues) and 12 (Internal Inconsistencies) are built in code. Points 8 (Termination and Exit) and 9 (Dispute Resolution) are written from focused evidence: hybrid search for the topic, with a keyword fallback over the clauses' page text. Executive Summary (point 13) is one constrained call over points 1-12, the risk lines and the verified Missing list, with a code guard that drops a gap claim when the Missing list is empty; a cited-sentence fallback is labelled "Assembled from cited sentences above."
- Drafting issues (`textQuality.ts`, code only, never model): unfilled blanks (`___`, `[ ]`, `___ days`) and reviewer comments (`Commented [..]`, `[TBC]`, bracketed notes), grouped by clause and page with counts in point 11. Signature material is excluded in any format: Witness/Signed/In the presence of, a capitalised party label followed by underscores, a label with a short name then underscores (`Licensor: Name ____`), and the trailing signature region (unless a schedule/annexure follows). Excluded lines are never attributed to a clause. One Medium risk per clause whose blank touches money, time or a party; comment text is never analysed as a term.
- Internal inconsistencies (`inconsistencyChecks.ts`): a finding needs two verified quotes, a shared subject and a shared party, and a one-line reason. Checks: irrevocable/non-terminable vs termination, arbitration vs exclusive court, two deposits/guarantees for one purpose, two figures in one clause for the same subject and kind, and different termination notice periods (escalation/review intervals never count). Different categories or parties never flag; an empty result is normal.
- Risk Register has an Affects column. `inferAffects` fills it from a party named in the risk text, then its roles, then the clause's obligations, else "Both/unclear" (never "Not identified"). The reviewing side frames suggestions; Neutral shows the affected party. Suggestions must name the concrete change. The rubric also looks for irrevocable grants, tax allocation, assignment/consent restrictions, unilateral rights and one-sided indemnities; neutral obligations with no exposure are not risks.
- Law names dedupe by `lawKey` (year and punctuation ignored), so "…Act" and "…Act 1999" count once.
- Law references name the Act that fits the issue; the clause prompt says not to default to the Indian Contract Act. Statutory Compliance (`statutory.ts`) keeps at most six Acts: those engaged by a risk or missing item, plus the Acts central to the document type from a small subject map (lease/occupancy, agreement, deed/sale, notice; unknown types get none). A model-proposed Act is kept only when it is central; unrelated Acts are omitted. Dedupe by `lawKey`.
- Executive Summary (`summaryGuard.ts`): summary sentences are validated by citation only (they carry no point number). Absence claims are dropped unless the verified Missing list has an entry; escalation-type matches are ignored. The fallback is short: nature, parties and key terms, at most six cited sentences, labelled "Assembled from cited sentences above." The synthesis and summary prompts state that the entire reply is one JSON array with object elements (never bare strings) and include an example; this keeps `bad_json` from prose replies down.
- Overview points 8 and 9 state the actual terms (who may terminate and on what notice; who decides a dispute, forum, waiver), not only that a process exists.
- Risk Register: clause rubric excludes generic disclaimers, forward-looking warnings, "no assurance" boilerplate, selling/jurisdiction restrictions, definitions and neutral procedures, judged by effect on a party (liability/right/remedy limits stay risks). A batched validation pass (`riskReview.ts`, 20 per call, High and Medium only) keeps, downgrades or drops each risk and removes duplicates (same clause and issue); the report shows "N risks after validation (M dropped)". Fail open if a batch fails. Never-drop guard (`riskGuard.ts`): a term that puts a cost or liability on a named party (cost keyword plus bear/borne/pay/liable/indemnify/forfeit, with a party name or a generic role) can be downgraded but not dropped; boilerplate mentioning fees stays droppable. Drops and reasons are stored and shown in a dev-visible list.
- Dates and Amounts are two tables (Dates: date/what it is/fixed or relative/clause/source; Amounts: amount/what it is for/payer to payee/when due/clause/source). A missing purpose falls back to the verified quote.
- Prompt Result (run-start custom prompt): one small non-reasoning request-check call (`prompt-interpret-v1`, `VITE_PROMPT_INTERPRET_MODEL` → `VITE_SEARCH_MODEL` → gpt-4o-mini, ~300 output tokens) reads the prompt as data and returns one JSON object `{subjects, wholeDocument, parties, wantsRisk}` (`promptInterpret.ts`). It is recorded as task `pi` (counted in the run and the pre-run estimate) and reused on retry. Code validates it against the prompt: a subject or party word that does not appear in the prompt is dropped; a party word becomes a required subject only when it matches the document's party list or defined terms, otherwise it is framing (like the reviewing side). `wholeDocument` or `wantsRisk` turns on the broad route. If the call fails, times out or is not one valid object, every guard is left strict and the section shows "I could not read this request clearly. Please try again." with the failed task behind "Retry failed only" — never a guard bypass and never "Not clearly stated".
- Prompt Result (evidence and length): the clause call still returns up to 5 short `promptAnswer` quotes per clause. A broad request also runs a coverage pass over up to `VITE_DEEP_PROMPT_EVIDENCE_CHUNKS` (default 10) extra sections (hybrid search plus the request's own terms, `promptEvidence.ts`) and uses the run's verified findings — risks, obligations, payments and dates, up to `DEEP_PROMPT_REPORT_FINDINGS` (120, with the remainder counted in the stats line) — as evidence. On the broad route a quote needs any one of the validated subject groups (none required when the request names no subject), and quotes that fail go to the unchanged second-chance check, which is judged against the validated subjects rather than the raw request; the strict every-concept guard and the plain message are unchanged for narrow/standard prompts. The request is split into the user's own parts (`?`/list items, never on "and"; max 6, the rest answer under "Other parts of your request") and each part is answered by its own call (`prompt-synthesis-v5`), with the user's wording as the heading. A part with no supporting quote shows "Not clearly stated in the document." (or, for a broad request, "I could not find passages that clearly answer this request." via `notStatedText`) and makes no model call. Answers are as long as the request needs (caps: narrow 800, standard 2000, broad/list 3000 tokens); every element cites a verified quote id, and an id the model writes into the text is stripped. A cut-off answer (`finish_reason=length`) is never split: that part is retried once at twice the budget (ceiling 6000) with a "answer more tightly" line, and a second cut-off marks the part truncated with a visible note, keeping only complete cited elements. The default/chat path keeps the runner's split and `prompt-synthesis-v4`. Deep-path calls use `VITE_ANALYSIS_MODEL` with no reasoning effort. The stored `PromptResult` keeps `answer` (flat, for the exports), `groups` and `sourcesMore` unchanged, and adds `parts`, `truncated`, `stats` (including `moreFindings`) and optional `notStatedText`. On screen the answer is prose and bullets with `[1]` markers that jump to a separate numbered Sources list (clause, page, verified quote); DOCX/HTML are unchanged. A failed write-up still lists the verified quotes; retry-failed re-queues the part answers. The Deep Analysis page no longer has a post-report Ask box.
- Post-report prompt (`promptOnReport.ts`): chat-only now. Retrieval mode reads the most relevant chunks (`VITE_PROMPT_RETRIEVAL_CHUNKS`, default 12) selected by hybrid search, then synthesises; whole-document mode reads every chunk (or the `chunkIndexes` subset that chat's pre-filter passes). The result records its mode and chat shows "Based on the N most relevant sections of C", with a "Scan whole document" action. The general analysis is not recomputed.
- Answer relevance (custom prompt pass, `promptPass.ts`, `answerGuard.ts`, `questionTerms.ts`): each prompt-pass item needs a one-line `why` saying how its quote answers the request; an item without one is rejected, and a chunk with only a related term or number returns []. Before synthesis, an answer is kept only when its quote has every concept of the request. A concept is a significant term of the request (stop and generic words removed) or one of its synonyms from `synonyms.ts` (security deposit/deposit/security; landlord/lessor/licensor; tenant/lessee/licensee; termination/terminate/cancellation/expiry; refund/refundable/repayment/return; notice/intimation). A word outside the map matches only itself (six-character prefix). Synonyms widen the match, never drop a concept: a quote must still carry each concept the request needs, so a rent-in-advance clause or a payment-default notice does not answer a deposit or termination question. The map is kept narrow on purpose ("advance", owner/vendor/seller/purchaser/buyer are excluded). With no significant terms nothing is rejected. The chunk pass and the synthesis prompt both tell the model that a synonym still answers the request (prompt versions `custom-prompt-v2`, and `prompt-synthesis-v4` on the default path or `prompt-synthesis-v5` for the Deep Analysis prompt). Chat routing and the scan pre-filter keep literal terms. Synthesis (`prompt-synthesis-v4`) writes "Not clearly stated in the document." when no answer survives, and a call that failed is still reported as an error, not as "not clearly stated". After synthesis, a sentence is dropped when a number in it is not in its cited quote, or when the unit the quote gives next to that number (Rs, %, day, month, year, week) is missing from the sentence; a clause or section reference is not an amount. These guards apply to every synthesis: chat retrieval and whole modes, the post-report prompt, and the inline Prompt Result (the clause call's `promptAnswer` quotes have no `why`, so the subject check is the one that applies). The clause-call prompt itself is unchanged. Known trade-off: a word outside the synonym map still has to match literally, so an unlisted synonym is rejected and gives "not clearly stated" rather than a wrong figure. Adding a word to `synonyms.ts` is the fix; check it does not map a different thing in another contract type.
- Second-chance relevance check (`answerRelevance.ts`, `checkRelevance` in `promptPass.ts`): only quotes the deterministic subject guard rejected are sent to the model, in batches of up to ten (one call per batch; no call when nothing was rejected, and quotes that pass never reach the model). The prompt asks yes/no plus a one-line reason. A "yes" keeps the quote and its reason replaces its `why`; "no", a missing verdict or a failed call leaves it rejected (fail closed). The check never replaces the deterministic/synonym check and runs before the synthesis; the synthesis re-queue (retry) happens after it. Per-quote decisions, call count and any error are stored on `promptResult.relevanceCheck` (in the report and in Supabase) and shown in the Deep Analysis dev panel on `/?page=analysis`. Task id suffixes `rj`, `rj2`, … with `answer-relevance-v1`. Chat's pre-send estimate does not include this check (it runs only on rejected quotes and cannot be predicted before reading).
- Clause Breakdown is collapsed by default on screen (exports unchanged).
- No Timeline section. Section numbering follows the model (7 sections without Prompt Result, 8 with it).
- Clause table rows: Summary always; others only when they have content. No Missing row (the missing protections are in the Risk Register). Clauses sort by clause number, numerically; underscores in labels are shown as spaces.
- Coverage: no clause count in structure-free runs or when zero; chunk and page coverage only.
- Retry-failed refreshes the stored prompt, prompt version and fingerprint from the current plan before re-queuing a failed task, so a retry after a prompt fix uses the new prompt. The synthesis task is re-queued with the current template too.
- The failed-task table shows the first 300 characters of the stored raw response for each failed attempt, so `bad_json` and similar failures can be diagnosed without the browser devtools.
- Tests use the hosted Supabase project (`testSupport.ts` helpers); `runAnalysis.retry.test.ts` covers retry.

## Drafter (D1: storage + Brief form)
- `/draft` lists drafts (title, updated time, status chip, reference count; Open, Delete with confirm). `/draft/new` and `/draft/:draftId` are the Brief form: title (optional, derived from the first ~60 chars of the instruction when blank), instruction, Reviewing for (Licensor/Licensee/Neutral, default Neutral), reference documents. There is no autosave and no separate Save button: one primary **Continue** validates, creates/updates the draft, best-effort syncs, reads the plan when needed, and opens `/draft/:draftId/plan`. A small secondary **Save and close** saves without a model call and returns to `/draft`. An unchanged Brief with a fresh plan opens the plan without re-reading; a changed Brief is saved and re-read automatically. A read failure leaves the saved Brief and shows "Try again".
- `src/drafter/` is plain TypeScript with no UI imports. `store.ts` opens a **separate** IndexedDB `legal-drafter` (v1, stores `drafts`, `draft_deletions`); `pipeline-harness` is never opened for writing and its name, version and stores are locked by `harnessDb.test.ts`. `sync.ts` maps to the Supabase `drafts` row. `references.ts` resolves the picker. `brief.ts` derives the title.
- Draft record: `{ id, userId, title, instruction, referenceDocIds, reviewingFor, status: 'brief', particulars: null, sourcePlan: null, outline: null, clauses: {}, schemaVersion: 1, createdAt, updatedAt, syncedAt? }`. The null fields are placeholders for D2-D6. `status` also allows `planned`/`outlined`/`generating`/`done`/`failed`, unused in D1.
- Sync is local-first and never blocks the UI: IndexedDB is the working copy, Supabase is pushed best effort after Save and retried on `/draft` load. Every sync call swallows errors and returns a falsy result; an offline or signed-out user keeps working. A failed push leaves the local record untouched and `syncedAt` unset (pending = `syncedAt !== updatedAt`).
- Pull on `/draft` load is **insert-only**: rows missing locally are added; a local draft is never overwritten. D1 conflict rule is local wins, whole-row upserts, last push wins. Cross-device edits to a draft that already exists locally are not merged (deferred to a later stage).
- Deletes are local-first with a tombstone (`draft_deletions`): the row is removed here immediately, the remote delete is retried, and a tombstoned id is never pulled back. The tombstone is cleared when the remote delete succeeds.
- Reference documents reuse the library's own Ready check (`isPrepared` from `src/ui/library/preparationState.ts`); only Ready documents are offered. A saved reference that is no longer Ready, or no longer on this device, stays attached and is flagged ("not on this device" / "not prepared") until the user removes it. Zero references is valid.
- `supabase/migrations/0006_drafts.sql` creates `drafts` (uuid id generated on the client, `user_id` default `auth.uid()` with cascade, `reference_doc_ids` jsonb, `reviewing_for` check, `data` jsonb for later stages, `schema_version`) with RLS owner-only. Apply with `npx supabase db push` (hosted, after link) or `npx supabase db reset` (local). No updated_at trigger, matching the chat tables.

### Drafter D2: instruction parsing (source plan + particulars)

- `src/drafter/plan.ts` is pure (aliases, input, validation, mode, stale check, stored readers). `planCall.ts` owns the call. `src/ui/drafter/planRun.ts` wires it (token, endpoint, model, raw copy) and saves the result.

Stored in `data.outline`; the tolerant reader returns null for a malformed stored outline. No migration.
- The model returns short source ids (`B1`…) mapped back to `sourcePlan.bindings`; unknown ids are dropped and counted. Titles cap at 120, purposes at 300, items at 150; a leading level 2 is promoted to level 1; invalid items are dropped and counted; exact duplicate titles at the same level are kept and flagged; zero valid items is `empty_outline`.
- Display numbers are computed in code, never taken from the model: level-1 clauses `1, 2…`, their sub-sections `1.1…`, level-1 schedules `Schedule 1`, their sub-sections `Schedule 1.1`; preamble/recital/signature/other and sub-sections under an unnumbered parent are unnumbered. Moving a main section moves its sub-sections; outdent puts a sub-section after its parent block; deleting a main section deletes its sub-sections.
- Model: `VITE_DRAFTER_OUTLINE_MODEL` → `VITE_ANALYSIS_MODEL` → `VITE_SEARCH_MODEL` → `openai/gpt-4o-mini`, cap 6000 tokens, via `streamChat` (same proxy path as chat and the plan call). `finish_reason=length` is never parsed ("The outline was too long to finish"); empty/bad JSON/non-object are visible failures with Try again. No automatic retry or fallback model. Raw reply in `localStorage` (`legal-app.draft.<id>.outlineRaw`), never synced.
- Reference structure hints (`src/drafter/refStructure.ts`, read-only): for documents with no binding or only style bindings, up to 5 documents, read `chunks` and keep `chunk.heading` for `startKind` clause/section/part, deduped, max 60 headings and 90 characters each. Fewer than 3 headings means nothing is sent for that document ("no usable headings"). Bound (verbatim/adapt) sources are never read. The prompt labels these as incomplete; the UI never claims they are authoritative.
- Outline screen: "Here's the structure I propose", editable titles and purposes, computed numbers, Up/Down/Indent/Outdent/Delete, add sections, per-section source tags, unused-source notes with "Attach to…", a duplicate-title hint, "Change it with instructions" (refine call with the current edited outline as the previous outline; a confirm says the model may reword manual edits), a stale banner, "Looks good, continue" (saves the outline and writes `outlined`), "Back to plan" and "Start the outline again". There is no Advanced section: its read-only model/created time, dropped/duplicate counts, raw reply, fingerprint and notes are removed from the UI. The dropped-items count is a one-line inline note only when greater than zero; duplicate titles stay inline. The stale rule is `outline.planFingerprint !== planFingerprint(draft)`: Confirm is blocked until the outline is updated; editing the Brief or changing the plan never deletes the outline.
- Draft list status labels are plain and UI-local (`src/ui/drafter/statusLabel.ts`): Brief, Plan ready, Outline ready, Writing, Done, Failed. Stored status values are unchanged.
- `src/drafter/brief.ts` `draftStatusLabel` is now unused (left in place).

### Drafter D4a: bound sources (read-only reference text)
- After the outline is confirmed, the Outline screen's primary button ("Continue" when already confirmed) goes to `/draft/:draftId/sources` when any `verbatim`/`adapt` binding exists, else `/draft/:draftId/write`.
- `src/drafter/resolveRef.ts` (plain TS, harness DB handle passed in) resolves every `verbatim`/`adapt` binding read-only over `documents`, `pages` and `chunks`; style bindings are not read. It never writes to `pipeline-harness` (a test asserts the three stores are unchanged).
- Fields relied on: `documents.pageCount/name/prepFingerprint` (missing doc → `not_found`; pageCount 0 falls back to the max stored page), `pages.pageNo/text` (missing pages skipped), `chunks.pageMarkedText || text`, `chunks.clauses/clauseFrom/clauseTo/heading/pageStart/pageEnd/index`, filtered to the document's `prepFingerprint` when both are set.
- Clause targets: numeric labels match `clauses`/`clauseFrom`/`clauseTo`; contiguous split parts merge; two separated groups (or a numbering restart) are `ambiguous` with candidates, never auto-picked. A numeric match must also share a keyword with `appliesTo`, else it is `ambiguous`. Non-numeric values match `heading` text. Pages use `parsePageRange` against the page count. Topics use deterministic keyword scoring (own Unicode tokeniser, 6-char prefixes, top 3, minimum score 1 for one term / 2 for several) — the retrieval worker is deliberately not used. `whole` resolves only for documents ≤ 6 pages, else `too_broad`. Source text is capped at 12,000 characters with a visible `truncated` flag.
- Stored `draft.sourceText = { resolutions, resolvedAt, planFingerprint, outlineFingerprint }`. Source text stays in IndexedDB; Supabase gets metadata only (`sourceTextForSync` blanks each candidate `text`), and the tolerant reader accepts it. `outlineFingerprint` (in `outline.ts`) covers item id/level/title/purpose/kind/bindingIds.
- A source is usable only after the user confirmed it on the Sources screen (`userConfirmed`); `usableSource` returns nothing before that, so unconfirmed text can never reach the model.
- Sources screen: one card per bound source with plain status wording, candidate radios with previews, "Pick pages instead", "Skip this source", and one primary "Looks good, continue" that is disabled until every source is chosen or skipped. Stale plan/outline shows a banner and a "Read the documents again" action.
- `sourceTextReady` gates writing: not stale, every verbatim/adapt binding confirmed or skipped, chosen text present on this device.

### Drafter D4b: clause-by-clause writing
- `/draft/:draftId/write` writes the confirmed outline. The engine lives outside React (`src/ui/drafter/writeRunner.ts`): navigating between app screens does not stop a run; closing the tab kills in-flight calls, finished clauses are already saved, and reopening attaches to a run still in progress or starts the remaining sections automatically (a stopped run shows Resume). Stop finishes in-flight calls and pauses.
- `src/drafter/write.ts` (plain TS): item fingerprints, phases, model input, ref tokens, the engine, stored readers. `writeCall.ts` makes one plain-text call through `streamChat`; `ledger.ts` extracts defined terms; `writeEstimate.ts` is the pre-run estimate. No task types, no `runTask`, no harness writes.
- `draft.clauses[itemId] = { text, status: pending|writing|done|failed|verbatim, itemFingerprint, sourceBindingIds, model, generatedAt, durationMs, error?, errorCode?, copiedFrom?, truncated?, unknownRefs? }`; `draft.writeRun = { startedAt, finishedAt, calls, retries, rateLimitEvents, rateLimitWaitMs, stopped? }`. Both live in `data` jsonb (no migration); tolerant readers return `{}`/null for malformed values.
- Item fingerprint = hash of title, purpose, kind, binding ids, chosen source text per binding, and the plan fingerprint. A clause is stale when it differs; stale text is flagged, never deleted. Editing the outline or a source changes the fingerprint.
- Verbatim: an item with exactly one binding that is `verbatim` and confirmed copies the source text unchanged, with no model call, status `verbatim`, `copiedFrom` and the UI note that names/figures are the source's.
- All other items: one plain-text call per item, `VITE_DRAFTER_WRITE_MODEL` → analysis → search → `openai/gpt-4o-mini`, cap 3000. `finish_reason=length` is a failure ("cut off"), never saved as done; empty output is a failure. Retries only timeout/network/stream_interrupted/empty_output/http_429/http_5xx, max 3, backoff 500 ms × 2^attempt; a shared gate holds workers after 429/network/5xx; after two consecutive 429s the batch size drops by one (min 1).
- Phases: 1 = preamble/recital, the first 6 items, and title/purpose matching definitions/parties/party/term/consideration/payment/rent/deposit (sequential, outline order); 3 = schedule/signature (last); 2 = the rest, in batches of `VITE_DRAFTER_CONCURRENCY` (default 3).
- Input: brief, particulars (`[●]` when missing), the full outline as `S1..Sn`, this item, confirmed source text with its mode (style gets no text), the defined-term ledger so far, and one-line summaries of related sections. All user content is in DATA blocks. Cross-references must be `{{ref:Sn}}`; code replaces known tokens with computed numbers at display, unknown ids stay visible and are listed in `unknownRefs`.
- The ledger is extracted deterministically from each finished text: `(the "Term")`, `"Term" means …`, `"Term" shall mean …`, and an unquoted `Term means …`; the definition is the sentence, capped at 300 chars, first definition wins.
- Each result is written to IndexedDB before the next item; `writing` items found on resume are rewritten; resume runs only missing/pending/failed/stale items. The Write page's automatic batch passes `onlyItemIds` with the pending/stale/non-failed ids, so failed sections are left untouched for their own "Try again"; `WriteEngineOptions.onlyItemIds` is optional and absent calls behave exactly as before. Supabase sync is best effort after the run. A per-draft `navigator.locks` lock (`draft:<id>`) prevents two tabs writing; without it, no lock.
- Draft status: `generating` while running or paused, `done` only when every item is done/verbatim and none stale, `failed` when a finished run has failed items. Token counts are unavailable from the proxy, so only durations/calls/retries/429 counts are stored.
- Write screen: no Start button. Opening `/write` starts a batch automatically for pending/stale/missing items (verbatim copies included) through the existing runner and `draft:<id>` lock. It does not start when the outline is stale, a **needed** source is stale/unconfirmed (`sourceTextReady`), every section is fresh done/verbatim, another tab holds the lock, or the user pressed Stop in that visit. Leftover stale sourceText with no verbatim/adapt bindings does not block (`sourceGate`). A run already in progress is attached to, not started again. A per-visit ref plus the runner's `runners.has` check prevent double starts, including StrictMode. Failed sections are never auto-retried: they show "Needs attention" with "Try again"; a batch passes `onlyItemIds` for the pending/stale/non-failed items. The estimate is a small informational line (sections, rough minutes, verbatim copies), not a gate. The progress bar is derived from stored clauses: fresh done+verbatim over total, stale excluded, failed/pending not done, plus a live in-flight "writing now" count; it updates after each saved section, is clamped, and shows correctly on a partial revisit. `writeRunner` keeps listeners before/after a runner exists, tracks in-flight calls and exposes the active flag; it wraps listener calls and cleans the runner in `finally`, so a thrown listener cannot leave a stale entry. Each section shows its status, expands to the read-only text (`[●]` highlighted, refs rendered), and offers "Write this section again" or "Try again". At the end: "All sections written", open `[●]` count, stale count, "Finished in Xm Ys · N retries" from the stored `writeRun`, and "Review and download". There is no Advanced section: timings, run dates, rate limits, ledger terms and read-only counts are removed; the run line and stale count are inline. Every `blocked:*` or `wait` decision has a plain visible reason from `writeStartReason`; the existing banner is used where it already states that reason.
- `src/ui/drafter/writeProgress.ts` (pure, `writeProgress.test.ts`) classifies items and computes `{ done, total, percent, label, complete }`, the auto-start decision (`attach`, `blocked:outline`, `blocked:sources`, `blocked:lock`, `finished`, `wait`, `start`, never twice), the source gate (stale sourceText only counts when `sourceTextReady` is false) and the plain reason for every blocked/wait result. `src/ui/drafter/writeRunner.test.ts` covers runner cleanup after a run and a throwing listener. `src/ui/drafter/briefContinue.ts` (pure, `briefContinue.test.ts`) decides navigate / read / save-and-read / save-and-navigate / create-and-read for the Brief.

### Drafter D6: review screen and DOCX download
- `src/drafter/assemble.ts` (pure) turns the outline and written clauses into one ordered block list: title (`draft.title` or docType), optional docType subtitle, numbered headings (`numbering` from code; unnumbered kinds have no number), paragraphs split on blank lines, and pipe-separated rows as tables (first row = columns, a markdown separator row is dropped, at least 2 rows). `{{ref:Sn}}` becomes the computed number (or the title when unnumbered); unknown ids become `[unknown reference]` and are counted. `[●]` placeholders are kept and counted. Failed/pending sections keep their heading and no body. Verbatim text is included with no extra annotation.
- Stats: `{ sections, placeholders, unknownRefs, staleSections, failedSections, pendingSections }` (stale via `itemFingerprint`). `exportGate(stats)` blocks when there are no sections, or any pending/failed section; it allows with plain warnings for placeholders, stale sections and unknown references. `draftFileName` = sanitised title + `YYYY-MM-DD.docx`.
- `src/drafter/export/docx.ts` is the Drafter's own writer (no `src/export` import): Times New Roman 11 pt body, justified, real Heading 1/2 (number in the text, never Word auto-numbering), real tables, yellow-highlighted `[●]` runs (`HighlightColor.YELLOW`), title block, footer "AI-assisted, requires lawyer review" + page numbers. The build yields every 20 blocks.
- `/draft/:draftId/review` renders the same blocks read-only with `[●]` marked, shows the summary line and the gate's plain blockers/warnings, and downloads the DOCX from a Blob. The Write screen's completion button is "Review and download", enabled when the gate allows (warnings do not block) and disabled with the first blocker otherwise. Draft status behaviour is unchanged.

#### Drafter D6.1: legal-document layout (formatting only)
- Every layout feature switches on from the structure already stored (level, number, kind, text pattern), never from a document type or keywords. A short notice stays a title, paragraphs and a footer; a long agreement gets the full treatment. Neutral style: serif, black text, no colour.
- `DraftBlock.heading` gains only an optional `sectionKind` (the outline kind). Cover, contents and signature tables are writer-only: the block list is unchanged, so the review screen stays a content preview. `headingTitle`/`headingLabel` and `listLines` live in `assemble.ts` and are shared with the screen.
- Cover and contents appear only from **15 level-1 headings** up (level-2 items never count). Cover: centred title, optional docType subtitle, the verbatim `between … and …` line from the preamble (omitted when absent or when either side has no capital letter), the date, then a page break. The contents is a real Word TOC field over Heading 1/2 (`TableOfContents`, dot leader, `beginDirty`) with entries generated from the headings, on its own page. `features.updateFields` makes Word refresh the page numbers on open; LibreOffice shows the entries and updates them with "Update Index"; Google Docs may show the entries without numbers or drop the table, and the body is unaffected. The contents heading is deliberately not a Heading style, so it never lists itself.
- Headings: code-generated number, a real tab, the title, hanging indent (0.5" level 1, 1" level 2) so the number sits in the margin column and wrapped titles align under the title. Long numbers (`Schedule 1.1`) keep the number-and-space form. A `schedule` heading starts a new page; a title that repeats its own number (`Schedule 1 - Floor Plans`) loses the repeat in the writer and on screen, but `Schedule 10 …` under number `Schedule 1` is left alone. A `preamble` heading is centred.
- Body: justified, 1.15 spacing, widow control, `keepNext` on headings. A paragraph block is laid out line by line only when a line opens with `(a)`/`(i)`/`1.1`; those lines get a hanging indent (roman `(i)` one level deeper only when it follows `(a)`), and the model's text is never reordered or renumbered. Recital blocks also accept `(A)`.
- Defined terms: the quoted token in `(the "Term")` and `"Term" means`/`"Term" shall mean` is bold. A single tokenizer carries both that and `[●]` highlighting and provably adds, drops and rewords nothing.
- Signature blocks (`sectionKind: 'signature'`): two or more `Role: [● name] ____` lines become a borderless table, one column per party, three to a row, with the signature rule and a `Date: ____` line under each; `Witness…` lines move to a row below. Unmatched text stays a paragraph in its original position. Fewer than two matches falls back to plain paragraphs with no added label. No text is lost in either path.
- Header: the document title, right-aligned, small, grey — omitted on the cover via `titlePage` plus an empty first header/footer. Footer: the review notice and `Page X of Y`. Tables keep their header-row repeat and gain a light `F2F2F2` header fill and roomier cells.
- Known consequence: the cover counts as page 1, so the contents reads "Page 2 of N". A separate section with restarted numbering would break the TOC scoping (a TOC only sees its own section), so it is accepted.
- Tests (`export/docx.test.ts`, `assemble.test.ts`): 5 sections stay plain, 15 level-1 sections add cover + contents, 10 level-1 + 8 level-2 do not; schedule page break and prefix dedupe; `(a)`/`(i)` indent XML and a plain paragraph without; defined-term bold with the document text unchanged (compared whitespace-insensitively); signature table vs paragraph fallback with no text lost; header present and absent on the cover; footer page fields; table header repeat and shading; 150 sections still build.

## Chat (`/chat`, `/chat/:sessionId`)
- General chat with no document. The request carries only the system prompt and the thread; no retrieval. The thread sent to the model includes only messages that have no document context (`generalHistory`), so a General answer is never grounded in an earlier document answer.
- Document chat: the composer's "Ask about" picker lists only Ready documents (`isPrepared`); General is the default. Each message stores its own document id, name (as at send time), and for replies the mode and citations. Switching documents per message is allowed; a reloaded thread keeps each message's context.
- Routing (`src/chat/route.ts`, pure): "Scan whole document" → whole. Otherwise, if the document has a saved report (`analysis_reports`, else Supabase `reports`) and a question's specific words all appear in one row of the report model (amounts, dates, obligations, risks; the missing list for "missing"; the summary for "clause N"), the answer is the matching rows, cited to their source, with no model call (mode `saved`). Anything else → retrieval.
- "Scan whole document" is offered only when `wholeModeAllowed(doc.pageCount, VITE_WHOLE_DOC_MAX_PAGES)` is true: the page count must be known and at most the limit (default 10; `src/ui/chat/wholeMode.ts`). An unknown/zero page count fails closed. A long document hides the checkbox and shows "This document is long. Ask a specific question here, or use Deep Analysis for a full review."; a pending check is cleared and the question goes through saved/retrieval routing. The gate is at the ChatPage call site only, so `route.ts`, the answering code and saved/retrieval modes are unchanged.
- Retrieval and whole modes call the existing `promptOnReport` (`src/chat/documentTurn.ts`): the top `PROMPT_RETRIEVAL_CHUNKS` sections by hybrid search, or for whole mode the sections the pre-filter selects (below), then the prompt pass and one synthesis. The answer's sources are the verified quotes its sentences cite. Only the question is sent to the model for a document turn (no thread). Search that fails or matches nothing reads the first sections; the answer says so.
- Whole-document pre-filter (`src/chat/scanFilter.ts`, local, no model): the question's terms (`significantTerms`, the routing stop and generic lists) are matched by 6-character prefix against each section's words. A section is skipped only when it contains none of the terms; nothing is ranked. A question with no terms, or with terms that appear in no section, scans every section. `promptOnReport` takes an optional `chunkIndexes` (whole mode only; unset reads every section, so Deep Analysis and retrieval are unchanged). The estimate follows the draft, and each whole answer's text ends with a scan note such as "Scanned 420 of 650 sections; 230 had no match for your terms (…)". Synonyms that the terms miss are skipped; the note lists the terms so that can be judged.
- The saved report is never changed by chat; chat runs are tagged `runs.source = 'chat'` (analysis runs keep `source` null). The tag is written after the run, so a run that fails before it finishes stays untagged.
- Pre-send estimates (`src/chat/estimate.ts`): calls, input tokens, cost, and time. Time comes only from the document's last measured p95 call duration and concurrency; with no completed run it reads "time unknown". Retrieval's estimate uses the largest sections (upper bound); whole uses the pre-filtered sections (every section when the question has no terms).
- Sources: the assistant message shows its document, mode label (Saved report / Retrieval / Whole document) and "Clause N · p. X" buttons, capped at four with "+N more sources" for the rest (the stored message keeps every citation). A button opens `CitationPanel` (the Deep Analysis slide-over) with the stored PDF page. Stored citations are page, clause and quote only; chunk text is not stored.
- Known limit: a document question that depends on an earlier document answer is not answered from that history (the model sees only the question and its excerpts).
- Pages: `src/ui/app/pages/ChatPage.tsx` (session list, thread, composer). Persistence: `src/chat/store.ts` (takes the Supabase client as a parameter). Streaming: `src/chat/stream.ts` (own NDJSON reader, same `ai-proxy` contract as the runner; the runner's `callModel` is unchanged). Thread windowing and titles: `src/chat/thread.ts`. Error text: `src/chat/errors.ts`.
- Tables: `chat_sessions` (id, user_id, title, created_at, updated_at) and `chat_messages` (id, session_id, role `user`/`assistant`, content, created_at, document_id, document_name, mode `saved`/`retrieval`/`whole`, citations jsonb). Owner-only RLS (`user_id = auth.uid()`); messages follow their session; deleting a session cascades.
- A session is created on the first message and titled from it (60 characters). The user message is saved before the request; the assistant reply is saved only when the stream completes with a finish reason. A failed reply keeps the user message and shows Retry; no partial reply is saved.
- The session in the URL restores on reload. The session list and New chat are disabled while a reply streams. A reply that finishes after the user has left its session is saved but not drawn.
- Only the last `CHAT_HISTORY_MESSAGES` (30) messages are sent. The window never starts on an assistant message, so it can hold 29.
- Model: `VITE_CHAT_MODEL` (fallback `VITE_SEARCH_MODEL`, then `VITE_MODEL`, then the default). Output cap `CHAT_MAX_TOKENS` (4000).
- Markdown in replies: `react-markdown` + `remark-gfm` (tables, lists, bold). Raw HTML is not rendered; links open in a new tab.
- Each saved message (user and assistant) shows its `created_at` in local time (`formatMessageTime`: time today, otherwise day and time, with the year only when it differs) and a Copy button (`src/ui/chat/CopyButton.tsx`). Copy writes the stored `content` as written (Markdown source, no citation buttons) via `copyText`, which reports failure when the clipboard is missing or refuses; the button then says "Copy failed". Streaming and error bubbles have neither. No new columns.
- The shell footer shows "AI-assisted, requires lawyer review." on every page, including chat.
- Migration `0004_chat.sql`: apply with `npx supabase db push` (hosted) or `npx supabase db reset` (local).
- Migration `0005_chat_documents.sql` adds the document columns on `chat_messages` and `runs.source`. Apply the same way.
